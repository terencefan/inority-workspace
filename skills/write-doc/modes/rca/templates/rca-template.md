# Fault Analysis Template

Use this template when the user wants a structured Markdown fault analysis document and there is no stronger existing document convention.

## 标题

一句话总结当前最可信的故障边界。

## 背景

> 先说明这次分析是在什么上下文里发生的，以及为什么需要这份文档。

- 相关环境 / 集群 / 服务
- 触发事件或发现方式
- 当前分析目标

## 现象与影响

> 先讲清楚用户可见现象，再讲影响范围。

- 现象
- 影响范围
- 未受影响范围

## 调查范围与方法

> 说明这轮调查看了哪些边界，没看哪些边界。

- 主机 / 环境边界
- 只读还是可变更
- 用到的命令或探针类型

## 侦察结论

> 先放真正推动结论收敛的证据，而不是所有原始输出。

- 证据 1
- 证据 2
- 证据 3

可选子节：

- `关键 IP / 组件 alias`
- `故障示意图`
- `宿主机对比`
- `guest 对比`

每个子结论开头都先放一句简洁 blockquote，总结该小节的收敛结论。
每个子结论里都补一个 `可复现方法` 小段，写清进入路径、命令形状、重复次数和预期现象；如果初稿没写，先补一轮最小只读复现再落文。

## 已排除的故障原因

> 每个被排除的方向都要写“怎么查的”和“为什么能排除”。
> 只要本轮调查排除了某个方向，就不要只留在聊天或命令输出里，必须同步写回文档。

推荐格式：

### 1. 某个已排除方向

排查步骤：

1. ...
2. ...

排除原因：

- ...
- ...

## 当前结论

> 结论要和证据强度匹配；证据只支持到哪一层，就写到哪一层。

推荐拆成：

- `已由证据支持的事实`
- `当前更合理的工程推断`

## 仍未证实的部分

> 这里写不能直接下的结论，防止后续读者把推断当成事实。

- 未证实项 1
- 未证实项 2

## 复现步骤

> 复现步骤只覆盖当前最相关的故障面，并给出健康对照时为什么要一起跑。

- 前置条件
- 最小复现
- 健康对照
- 抓包或日志确认
