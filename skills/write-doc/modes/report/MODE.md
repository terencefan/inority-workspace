# Report Mode

适用于调研报告、侦察报告、现状分析、排障总结、运行态结论、对比结论和压测报告。

## 模式职责

- 先做只读侦察，再把事实、排除项、未确认项和建议收敛成调研报告。
- 强调 evidence-first，不把未经侦察确认的推测写成事实。
- 当报告依赖当前状态、远端资源或时效性事实时，先编排只读侦察，再落文档。

## 启动判断

先判断报告是否需要侦察：

- 需要侦察：涉及当前状态、故障、线上服务、主机、仓库、PR、数据集、S3、日志、API、监控、部署、性能、成本、安全、外部页面或任何可能变化的事实。
- 可以不侦察：用户只要求改写一份已完整给出的静态文本，且明确不需要验证事实。

如果需要侦察但缺少必要字段，优先补齐最小缺口：

- 报告问题：这份报告要回答什么？
- 环境边界：本机、某台主机、某个 repo、某个 URL、某个 run、某个数据集或某个服务。
- 只读边界：允许哪些只读动作，例如读文件、查日志、curl、kubectl get/logs、SQL 只读查询、S3 listing。
- 输出位置：直接回复，还是写到某个 `.md` 文件。用户没指定时，默认写到目标项目的 `docs/report/YYYY-MM-DD/` 日期目录，文件名使用 `<topic>.md`。

## 侦察编排

当报告需要只读侦察时，每条 reconnaissance dispatch 都应包含：

- authority/report 目标路径：已有草稿或目标文件；没有则写 `none`
- 环境边界：允许检查的主机、repo、URL、服务、数据集或资源
- reconnaissance 问题：一个可回答的事实问题
- 只读边界：明确允许的命令 / 查询类型
- 返回格式：`范围 / 方法 / 事实 / 未确认项 / 对规划的影响`

复杂报告可以拆多条独立 reconnaissance 问题，但每条都必须有独立边界。

## 模板

- `templates/report-template.md`
- `templates/benchmark-report-template.md`

## Validator

- 规则：`validator/rules.json`
- 错误码：`validator/error-codes.yaml`

## 文件与标题

- 标题必须以 `YYYY-MM-DD` 开头。
- 调研报告不要求以“设计文档”结尾。
- 普通报告的类型说明固定为 `当前文档类型：调研报告`。
- 性能压测、负载测试、容量测试和调优实验使用 `当前文档类型：压测报告`。
- 若用户未指定输出位置，默认使用 `docs/report/YYYY-MM-DD/<topic>.md`。

## 默认章节

- 默认二级标题顺序固定为：`侦察结论 / 范围 / 方法 / 事实 / 排除项 / 未确认项 / 建议 / 参考资料`。
- 压测报告二级标题顺序固定为：`目标 / 回退门禁 / 基线 / 实验矩阵 / 实验结论 / 最终结果 / 风险与后续 / 证据`。

## 压测报告规则

- 结论以吞吐量、延迟、成功率、资源利用率或用户明确指定的主指标为准，必须写明指标优先级。
- `目标` 只描述要最大化或改善的主指标、搜索范围和高峰判定，不混入回退条件。
- `回退门禁` 描述候选不可突破的底线，例如失败率、模型精度、业务决策一致率、输出契约和资源红线。触发任一门禁的候选即使吞吐更高也必须淘汰。
- `基线` 同时包含部署环境、数据集、输入处理、客户端与服务端参数、统计口径、原始性能和资源指标。缺少其中任一关键上下文的数值不能作为可复现基线。
- 基线采用可晋升的冠军链。候选相对当前冠军达到`显著正向`并通过全部回退门禁后，立即晋升为新的当前基线。原基线不得覆盖或删除，必须作为历史基线保留版本、配置、性能、精度、证据和被替代原因。
- 基线晋升后，所有尚未执行和需要重测的实验默认继承新基线的全部正向配置，只叠加各自的唯一变量。不得继续从更弱的历史基线分叉，除非实验目的明确是消融验证。
- 每次晋升都要同步更新基线版本表、实验矩阵的比较基准、组合路径和待测试配置。正在运行的旧基线候选窗口可以完成并归档，但不得用于新冠军后的横向排序。
- `显著正向`只代表性能晋升条件。模型候选还必须先通过精度统计等价、输出契约、失败率和资源红线等回退门禁，才能晋升。
- 实验矩阵必须包含`基线版本`列。当前基线使用独立行并在每个单元格使用浅绿色背景 `#dcfce7` 与深绿色文字 `#166534`。基线晋升时新增一行，不覆盖历史基线行，并把后续待测试实验的`基线版本`更新为新版本。
- 实验矩阵中的正向带符号百分比使用绿色 `#15803d`，负向带符号百分比使用红色 `#b91c1c`。颜色只辅助阅读，文本仍必须保留 `+`、`-`、百分号和显著性文字，不能只靠颜色表达方向。
- 每轮实验独立记录测试窗口、配置变量、样本量、并发、吞吐量、P50、P95、P99、失败数和结论。
- 实验矩阵是实时状态表。实验创建时立即新增一行，运行中更新状态，结果产生后立即补齐主指标和结论，不等整轮压测结束再回填。
- `实验结论` 中每组实验使用与实验矩阵第一列完全同名的独立三级标题，两者必须一一对应。标题后的第一个内容块必须是 callout。正向结果使用 `> [!TIP]` 和 `> 显著正向（+x%）：...` 或 `> 正向（+x%）：...`。负向结果使用 `> [!WARNING]` 和 `> 显著负向（-x%）：...` 或 `> 负向（-x%）：...`。与主指标无显著关系或被证明不是瓶颈的结果使用 `> [!NOTE]` 和 `> 不相关（+/-x%）：...`。尚未完成的方向使用 `> [!IMPORTANT]` 和 `> 待验证：...`。
- 每次形成新实验方向时，立即同时新增实验矩阵行和同名实验结论占位，不等实验启动或结束后再补文档。
- 每组实验的 callout 后必须使用 Markdown 表格展示结果，不使用散列 list。表格至少承载测试窗口、唯一变量、吞吐量、延迟、成功与失败、资源指标、精度、结论和证据中的适用项。
- 已完成实验的方向 callout 必须使用相对比较基准的带符号百分比，例如 `显著正向（+12.3%）`、`正向（+4.1%）`、`不相关（+0.6%）`、`负向（-3.2%）` 或 `显著负向（-11.8%）`。
- `显著正向` 要求主指标差异的 95% CI 全部大于 0 且 `p < 0.05`。`显著负向` 要求 95% CI 全部小于 0 且 `p < 0.05`。未达到统计门槛时不得使用“显著”。
- 性能显著性优先基于至少 3 个相互独立、各自连续不少于 300 秒的有效窗口。只有一个窗口时可以报告点估计百分比，但必须标记“显著性证据不足”。
- 每个完成实验的 Markdown 表格必须记录比较基准、重复窗口数、效应量、带符号百分比、95% CI、p 值和显著性判定。无法计算的字段写明原因，不得留空。
- 每组实验一旦得出阶段性结论，立即追加到报告。不得只保留最终成功方案，也不得覆盖此前的负向或不相关结论。
- 压测不能在单个正向实验出现后结束。必须识别所有可兼容的正向结论，将其组合到同一候选中，再围绕组合候选搜索主指标峰值。
- 压测默认至少同时部署两个服务，一个当前冠军基线服务和一个优化候选服务，在尽量相同的时间窗口、数据和客户端负载下对比。有资源时应并行部署更多相互独立的候选，缩短搜索时间并降低环境时变误差。
- 每轮并行候选必须明确唯一变量。出现正向结论后，下一轮创建组合候选，把已确认且兼容的正向改动叠加，再与固定基线和上一轮最佳候选同时对比。
- 最终输出不是最后一个实验，而是所有已测组合中通过回退门禁且主指标最高的组合。
- `最终结果` 必须汇总实验过程中出现的全部优化方向，至少记录方向、关键变量、性能变化、精度结论、正负向判断、是否进入最终组合和未采用原因。不得只展示冠军配置而省略搜索过程。
- 最终结果需要明确列出正向结论的组合路径，例如 `基线 -> 优化 A -> A+B -> A+B+C`，并说明每一步带来的增量。
- 将实验委派给 subagent 时，dispatch 必须分配独立资源，包括唯一实验编号、独立服务或 ModelSet、独立 GPU、独立压测客户端进程和独立输出目录。不得让多个 agent 修改或压测同一个可变服务。
- 并行实验之间不得共享会产生竞争的 GPU、CPU 配额、服务队列或客户端并发。若平台调度导致资源实际复用或相互抢占，相关窗口全部作废并重测。
- 主 agent 持有当前冠军基线、历史基线链、最有希望的组合候选和实验矩阵写权限。subagent 只返回各自实验的原始证据与结构化结论，由主 agent 统一复核和汇总。
- 主 agent 在每一轮优化实验开始前都必须联网搜索潜在优化方向。搜索问题要由上一轮的瓶颈、资源指标和代码路径驱动，优先使用官方文档、上游仓库、论文和框架维护者资料。
- 每轮搜索结果记录来源、方向、适用前提、预期收益、精度风险和是否进入实验。没有进入实验的方向也要说明原因，避免后续重复探索。
- 联网搜索不能替代本地代码和运行态验证。外部方向只有与当前模型版本、硬件、依赖和调用链匹配后，才进入独立资源实验。
- 主 agent 可以启动只读侦查 subagent，分别收集目标集群硬件拓扑、GPU 型号与互联、CPU/NUMA、部署方式、容器与依赖版本、服务日志、Prometheus 指标、火焰图或 profiler 数据。侦查结果必须保留时间窗口和资源标识。
- 只读侦查不得修改 ModelSet、重启服务或向正式压测服务注入额外负载。需要火焰图、torch profiler、Nsight 或主动探针时，必须使用独立服务、GPU 和输出目录，按执行型 subagent 的资源隔离规则管理。
- 每轮决策优先使用客观证据，顺序为运行态 profiler 与指标、目标环境真实代码和版本、本地代码、上游官方资料、经验推断。推断必须明确标注，不能替代缺失证据。
- 为实验创建或占用的闲时服务必须登记资源台账，记录服务 ID、资源、实验负责人、状态和对应实验。
- 实验完成、候选淘汰、窗口作废且不再复测时，及时停止对应闲时服务并确认 ready replica 归零。不得因报告已经写完而遗留实验资源。
- 最终收尾时逐项核对所有实验 ModelSet、Pod、压测客户端和 profiler 进程。只有用户明确要求保留的服务可以继续运行，并在报告中说明保留原因。
- “达到高峰”必须有相邻参数点、资源瓶颈或连续候选不再提升的证据。只有一个成功参数点不构成峰值证明。
- 模型类压测必须同时比较模型精度。实验矩阵增加精度列，每个涉及代码、算子、模型、prompt、量化或输出约束变化的候选都要使用固定同图测试集与基线配对。
- 模型精度至少记录业务决策一致率和适合该模型的误差或相关性指标。吞吐候选只有同时通过精度门禁，才能进入最终正向组合。
- 模型精度的“没有区别”必须使用统计等价检验，不能把传统显著性检验的 `p > 0.05` 解释为等价。优先使用配对设计、预先声明的等价界值和置信区间。
- 连续评分至少保留样本量、配对均值差、效应量、等价界值、95% 置信区间、TOST 或等价检验 p 值，以及 bootstrap 稳健性结果。业务二分类决策至少保留不一致数量、差值、等价界值和配对置信区间。
- 等价界值应由业务可接受误差和基线自身重复波动共同确定，并在查看候选结果前声明。不得为使候选通过而事后放宽界值。
- 多轮重复时同时报告单轮、候选自身波动、基线自身波动和逐样本中位数的最终等价结论。原始统计数据必须保留在实验结论表和证据文件中。
- 纯调度参数实验可复用同一模型实现已通过的精度结论，但报告必须明确标注“复用哪一候选的精度证据”，不能留空。
- 每个用于形成正向或负向结论的性能窗口默认必须连续运行至少 300 秒。少于 300 秒的结果只能标记为探测，不得进入最终实验矩阵的有效结论。
- 测试窗口内发生 Pod 或 ModelSet 驱逐、容器重启、服务被打挂、健康检查失败、客户端异常中断或非预期失败请求时，本轮作废。恢复后必须从新的连续窗口完整重测。
- 不得把驱逐或故障前后的数据拼接成 300 秒窗口。作废实验保留在证据中并标记原因，但不参与性能排序。
- 涉及 GPU 时，必须记录同一测试窗口的平均功耗、GPU 利用率、显存、SM、DRAM 和 Tensor 指标。采集不到的指标明确写 `不可用` 和原因。
- 基线和最终结果必须使用相同数据、输入处理、客户端并发和统计口径。存在差异时必须单独说明。
- 所有横向性能候选必须固定使用同一批真实主测试集，保持 manifest、有效样本、输入预处理和顺序口径一致。不得用不同数据集的结果直接排序。
- 有条件时准备多组固定真实测试集，覆盖不同语种、站点、图片尺寸、文件大小或内容分布。主测试集用于高频搜索和排序，其他测试集用于最终组合的泛化复测。
- 测试集必须版本化并记录稳定路径、样本数量、有效样本数量、预处理契约和选择方法。临时随机抽样且无法复现的数据不能作为正式结论。
- 模型精度配对使用固定同图测试集。若有多组数据集，最终峰值组合应分别报告每组精度，不只汇总平均值。
- 每个结论附原始结果路径、时间窗口、run id、日志路径或指标查询条件中的至少一种可复现证据。
- 用户明确吞吐优先时，尾延迟只作为观测项，不得仅因 P95 或 P99 上升淘汰吞吐更高的候选。

## 证据规则

- 优先使用本轮侦察里的原始命令、关键输出、文件路径、时间戳、URL、run id、commit id 或对象路径。
- 对被排除的原因，报告里必须写明排除步骤和排除理由。
- 对无法确认的事实，写在 `未确认项`，不要藏在正文里。
- 对只检查了单机 / 单 repo / 单 dataset 的结论，必须写明结论边界。
- 不粘贴密钥、token、cookie、AK/SK、完整凭据或敏感日志；必要时只写“已存在 / 未存在 / 匹配 / 未匹配”。

## 写作规则

- 涉及当前状态、主机、服务、仓库、日志、API、监控、数据集、S3、Kubernetes、数据库或网页事实时，默认先做只读侦察，再写报告。
- 报告正文不能把未经侦察确认的推测写成事实。
- 对被排除的方向，必须写明排除步骤和排除理由。
- 对无法确认的事实，明确写进 `未确认项`。
- 标题直接描述报告对象和问题，不写空泛标题。
- 默认结论先行；长报告也先给一句话结论。
- 涉及对比结论时，默认优先使用红黄绿灯表达强弱。
- 红黄绿灯优先用于对比表、结论表和选型权衡段，不要把整篇文档所有普通表格都染色。
- 互斥分类分布默认可以用 Mermaid `pie showData` 饼图，并同时保留表格数据。
- 饼图只能用于互斥且总量口径清晰的分布；多标签、可重叠、重复计数或可重复命中的统计不得画饼图。
- 使用 `侦察结论`，不要用 `关键结果` 作为主结论小节名。
- 每个主要 `侦察结论` 小节开头先给一句简洁 blockquote。
- 每个主要 `侦察结论` 小节都包含 `可复现方法`。
- 把事实、推断、建议分开；推断必须标明依据。

## 完成回报

完成时至少交代：

- 报告路径或已直接输出。
- 关键结论。
- 未确认项和剩余风险。
- 是否需要后续执行态 runbook，而不是在本模式里直接执行修复。
