# Report Mode

适用于调研报告、侦察报告、现状分析、排障总结、运行态结论、非压测型对比结论，以及持久化到项目中的事实清单、资源地址映射和 Markdown 表格。性能压测、负载测试、容量测试和调优实验统一进入 `benchmark` mode。

## 模式职责

- 先做只读侦察，再把事实、排除项、未确认项和建议收敛成调研报告。
- 强调 evidence-first，不把未经侦察确认的推测写成事实。
- 当报告依赖当前状态、远端资源或时效性事实时，先编排只读侦察，再落文档。

## 启动判断

先判断报告是否需要侦察：

- 需要侦察：涉及当前状态、故障、线上服务、主机、仓库、PR、数据集、S3、日志、API、监控、部署、成本、安全、外部页面或任何可能变化的事实。
- 可以不侦察：用户只要求改写一份已完整给出的静态文本，且明确不需要验证事实。
- 应切换 benchmark：目标包含吞吐、延迟、容量、性能基线、A/B 性能实验、调参、统计显著性、精度护栏或峰值搜索。
- 应直接进入 report：任务产出调查结果、语言与地址映射、资源清单、状态表格或其他事实型内容。默认生成项目内 `.md`，不要求用户额外说“放在项目里”“写成 Markdown”或“保存为 `.md`”。不要因为主内容只是一张表就降级为聊天文本、临时文本、TSV 或任意 reference 文件。
- 应切换外部交付：只有用户明确指定飞书或其他外部工具时，才不默认落项目内 `.md`，并改用对应工具的文档链路。

如果需要侦察但缺少必要字段，优先补齐最小缺口：

- 报告问题：这份报告要回答什么？
- 环境边界：本机、某台主机、某个 repo、某个 URL、某个 run、某个数据集或某个服务。
- 只读边界：允许哪些只读动作，例如读文件、查日志、curl、kubectl get/logs、SQL 只读查询、S3 listing。
- 输出位置：用户明确指定飞书或其他外部工具时使用对应交付面。否则默认写到目标项目的 `docs/report/YYYY-MM-DD/` 日期目录，文件名使用 `<topic>.md`。

## 小型事实表格报告链路

当主交付物是一张可持久化的事实表格时，完整使用 report 链路。不要因为内容少、行数少或主内容只有一张表而走快速精简路径：

1. 按启动判断完成只读侦察，核对表格事实、来源、时间点与覆盖范围。
2. 默认写入 `docs/report/YYYY-MM-DD/<topic>.md`。
3. 从 report template 开始，保留标准类型说明和全部必填章节。
4. 在 `侦察结论` 先写结论和可复现方法，不直接以表格代替报告结论。
5. 把表格放在 `事实`，并记录证据来源。不要额外生成 TSV，除非程序确实需要独立机器可读输入。
6. 在 `排除项` 记录未纳入表格的范围和理由。
7. 在 `未确认项` 标记可能漂移但尚未验证的条目。
8. 根据事实写出建议与参考资料，不因报告规模小而省略。
9. 执行 report validator 后再交付。

典型触发语句包括：

- “做一个表格放在项目里”
- “把每个语言和对应的 S3 地址整理一下”
- “把这些资源地址写成 md”
- “项目里留一份当前状态清单”

## 侦察编排

每条 reconnaissance dispatch 都应包含：

- authority/report 目标路径：已有草稿或目标文件，没有则写 `none`
- 环境边界：允许检查的主机、repo、URL、服务、数据集或资源
- reconnaissance 问题：一个可回答的事实问题
- 只读边界：明确允许的命令或查询类型
- 返回格式：`范围 / 方法 / 事实 / 未确认项 / 对规划的影响`

复杂报告可以拆多条独立 reconnaissance 问题，但每条都必须有独立边界。

## 模板

- `templates/report-template.md`

## Validator

- 规则：`validator/rules.json`
- 错误码：`validator/error-codes.yaml`

## 文件与标题

- 标题必须以 `YYYY-MM-DD` 开头。
- 调研报告不要求以“设计文档”结尾。
- 类型说明固定为 `当前文档类型：调研报告`。
- 若用户未指定输出位置，默认使用 `docs/report/YYYY-MM-DD/<topic>.md`。

## 默认章节

默认二级标题顺序固定为：`侦察结论 / 范围 / 方法 / 事实 / 排除项 / 未确认项 / 建议 / 参考资料`。

## 证据规则

- 优先使用本轮侦察里的原始命令、关键输出、文件路径、时间戳、URL、run id、commit id 或对象路径。
- 对被排除的原因，报告里必须写明排除步骤和排除理由。
- 对无法确认的事实，写在 `未确认项`，不要藏在正文里。
- 对只检查了单机、单 repo 或单 dataset 的结论，必须写明结论边界。
- 不粘贴密钥、token、cookie、AK/SK、完整凭据或敏感日志。必要时只写“已存在 / 未存在 / 匹配 / 未匹配”。

## 写作规则

- 涉及当前状态、主机、服务、仓库、日志、API、监控、数据集、S3、Kubernetes、数据库或网页事实时，默认先做只读侦察，再写报告。
- 报告正文不能把未经侦察确认的推测写成事实。
- 对被排除的方向，必须写明排除步骤和排除理由。
- 对无法确认的事实，明确写进 `未确认项`。
- 标题直接描述报告对象和问题，不写空泛标题。
- 默认结论先行，长报告也先给一句话结论。
- 涉及对比结论时，默认优先使用红黄绿灯表达强弱。
- 红黄绿灯优先用于对比表、结论表和选型权衡段，不要把整篇文档所有普通表格都染色。
- 互斥分类分布默认可以用 Mermaid `pie showData` 饼图，并同时保留表格数据。
- 饼图只能用于互斥且总量口径清晰的分布。多标签、可重叠、重复计数或可重复命中的统计不得画饼图。
- 使用 `侦察结论`，不要用 `关键结果` 作为主结论小节名。
- 每个主要 `侦察结论` 小节开头先给一句简洁 blockquote。
- 每个主要 `侦察结论` 小节都包含 `可复现方法`。
- 把事实、推断、建议分开。推断必须标明依据。

## 完成回报

完成时至少交代：

- 报告路径或已直接输出。
- 关键结论。
- 未确认项和剩余风险。
- 是否需要后续执行态 runbook，而不是在本模式里直接执行修复。
